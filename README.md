# Truck-Dispatch
Assign work to trucks and drivers, let drivers pick up jobs, and capture trips, miles, hours, and material tickets.

Today: a standalone Cloudflare Worker that serves the **Dispatch board**: it opens on the next **Working day** (US Eastern; on a Friday, Monday), shows one lane per Driver (name and usual Truck; a removed Driver only on a day he has work) and an Unassigned lane last, each with that day's **Assignments** as blocks reading "From → To" (or the note) in order, marked First and Then, with the Assignment's Foreman beside its job site ("TIUNY (Brody)"), and the Truck: one the Assignment names shows plainly, and with none named ("His own", the Driver takes his usual Truck) his usual Truck shows in grey, or nothing if he has none. Adding starts from the **+** on a lane (Unassigned included), which opens the composer in that lane: Pick up and Drop off as rows of Place chips and "Hauling what?" as Material chips, each with "Or type it" for a name not in the list (found, brought back or added by the Worker), a Foreman chip, filled in with the drop-off's usual Foreman if it is a job site, otherwise the pick-up's, which Dave can change or clear, and "Note or other truck" for the Truck chips ("His own" first, the default) and the note; a sentence previews it, Save needs only the day and puts it last in the lane, and the composer remembers the Places and Material for the next lane until **Close**. Tapping a block opens it in its lane (one at a time; tapping again closes it) as a sentence of chips, Driver, Material, From, To, Truck and Foreman, with its note: tapping a chip offers that list (Unassigned for the Driver, His own for the Truck, "Leave blank" for the rest), and each pick, or the note when left, saves on its own; a new Driver puts it last in his lane. **Do this first** and **Do this later** move it one place in its lane, each left out at that end. **✕** takes it off the day: on a Draft day it says Delete and deletes it; on a Sent day it says Cancel and the Assignment stays in its place, struck through and greyed, marked Cancelled, and opens only to **Put back**, which restores it (both count as Changed). On a Sent day a new Driver (or Unassigned) cancels it for the first Driver and adds it, marked Added, last in the new lane, where it stays open; on a Draft day it simply moves. On a day after today, **Copy today** copies today's Assignments onto it without their notes; The header shows the day's short date and its word ("Mon, Nov 23 · Next Monday", with a Holiday's name); an arrow each side names the Working day it goes to, skipping weekends and the six Holidays, and the left and right arrow keys do the same when no field has the focus; **Back to** returns to the next Working day from any other day. Below, the **week strip** has a tile for each day Monday to Friday and narrow Saturday and Sunday tiles, today's saying Today and the next day's Tomorrow, the day on screen filled and today outlined, each with the day's state (Sent, Changed, Not sent, "2 unassigned" on a Draft, or "–" for nothing; a day whose Assignments are all cancelled still has them, so it is not "–", and cancelled ones are never counted unassigned, since they are off the day) and a Holiday's name; tapping one shows that day, and the pager ("Nov 16 to Nov 22") moves a week at a time keeping the weekday. The strip reads the states again after any change on the Board and when the page regains the focus, and scrolls sideways on a phone. **Scheduler | Driver** in the header switches to the **Driver view** (at `/driver`): the first time it asks "Who are you?" with the active Drivers as large buttons, and the device remembers the Driver and the view in its browser storage (nothing is saved in the database), so it opens on his day; **Not you?** asks again and **Scheduler** switches back. It shows his today and tomorrow (calendar days, so a Sent Saturday shows on Friday): a day not Sent says "Dave hasn't sent Monday yet.", a Sent day with nothing for him says so, and otherwise his Assignments are large cards in Dave's order with the Material, Pick up, Drop off and the note, "Take Truck 53 for this one" when a Truck is named, and "Changed by Dave" with what each field was when Sent ("was Cobblestone"), "Added by Dave", or struck through and "Cancelled by Dave" (given to another Driver after the Send, it shows Cancelled to the first and Added to the second). It reads both days again, today included, whenever the page regains the focus. A second page, **Settings**, shows every list on one page (Drivers, Trucks, Places, Materials, Jobs, Foremen), each entry a chip with its key detail (a job site shows its usual Foreman, set in its panel); tapping one opens a panel that saves as you type, **+ Add** adds one, **Remove** makes one inactive after asking (warning how many later days still hold a Driver's Assignments), and removed entries are listed apart and can be brought back; nothing is ever deleted. **▲▼** by each Driver, Place and Material put them in Dave's own order, which the lanes and the composer's chips follow; a new or brought-back entry goes last (also one typed in the composer). Backed by D1 with **synthetic** Drivers, Trucks, Jobs, Places, Materials and Foremen only. Hub integration (at `/truck-dispatch/`), sign-in and production are later phases.

## Run it locally

Needs [Bun](https://bun.sh) **1.3.14**, pinned in `package.json` → `packageManager` to match the Hub and CI. A newer Bun rewrites `bun.lock` in a form CI rejects; install that version, or don't commit lockfile changes made with a newer one. No Cloudflare account needed.

```bash
bun install
bun run setup        # create the local D1, apply migrations, load synthetic data
bun run dev          # http://localhost:5173/truck-dispatch/
```

Tap **+** on a Driver's lane (or on "Unassigned"), tap the chips you know (or type a Place or Material that is not in the list), leave the Truck on "His own" unless the work needs a certain one, and Save; the Assignment appears last in that lane.

| Command | What it does |
|---|---|
| `bun run dev` | Vite + the Worker in workerd, with local D1 (`.wrangler/state`) |
| `bun run test` | Vitest (Worker against a real local D1, UI in jsdom) + migration-number check. Not `bun test`. |
| `bun run typecheck` | TypeScript for the page, the Worker and the scripts |
| `bun run build` | Build the page and the Worker into `dist/` |
| `bun run preview` | Build, then run the built Worker; the app answers at `/` and `/truck-dispatch/` |
| `bun run smoke <url>` | End-to-end checks against a running app (CI runs it on staging) |
| `bun run db:reset` | Delete the local D1 and set it up again |

## Layout

| Path | What |
|---|---|
| `src/` | React pages (React 18, react-router 6, Tailwind 3, shadcn/ui, sonner toasts, Hub theme tokens in `src/index.css`): Board at `/` (or the Driver view, on a device that chose it), Driver view at `/driver`, Settings at `/settings`, all also under `/truck-dispatch/` |
| `worker/src/` | Worker: removes the `/truck-dispatch` prefix, then serves the API (`api.ts`) or page files |
| `shared/types.ts` | API shapes used by both |
| `shared/base.ts` | The `/truck-dispatch` prefix, used by both |
| `shared/days.ts` | Day rules used by both, with no date library: Working days and the six Holidays, next and previous Working day, the word for a day (Today, Next Monday), short dates and arrow labels, and the Send rules: whether an Assignment is Changed or Added since its day was Sent, and a day's state (none, Draft with the count Unassigned, Sent, Changed; cancelled Assignments keep a day from being empty but are not counted Unassigned) |
| `migrations/` | D1 schema only. Create with `bunx wrangler d1 migrations create truck-dispatch <name>` |
| `seed/fixture.sql` | Synthetic Trucks, Drivers with usual Trucks, Jobs, Places, Materials and Foremen; `INSERT OR IGNORE`, safe to run repeatedly. No Assignments. |
| `wrangler.jsonc` | Local app (top level), `env.preview`, `env.staging` |

## API

Under `/api/` standalone or `/truck-dispatch/api/` under the Hub. No sign-in yet; Cloudflare Access protects previews and staging.

| Route | Answer |
|---|---|
| `GET health` | `{ ok, environment, commit }` |
| `GET drivers`, `GET trucks`, `GET jobs`, `GET places`, `GET materials`, `GET foremen` | `{ drivers: [{ id, name, defaultTruckId, sortOrder, active }] }`, `{ trucks: [{ id, number, hcssCode, hcssGuid, active }] }`, `{ jobs: [{ id, name, jobNumber, active }] }`, `{ places: [{ id, shortName, fullName, kind, jobId, usualForemanId, onTruckMap, sortOrder, active }] }`, `{ materials: [{ id, name, sortOrder, active }] }`, `{ foremen: [{ id, name, active }] }`. Drivers, Places and Materials come in Dave's own order (`sortOrder`, 1 first), then those with none (`sortOrder` null) by display name; the other lists by display name (name or number): active entries only; `?include=inactive` for every entry. A Place's `kind` is `plant`, `job_site`, `shop`, `yard` or null (Settings offers shop and yard as one, Shop or yard, saved as `shop`); its geofence code is not part of the API, only `onTruckMap`, whether it has one, which is never saved from the page. Only a job site has a `usualForemanId`; it is emptied when the Place stops being one, and an Assignment keeps its own Foreman, so changing it never rewrites a planned or past day |
| `POST drivers`, `POST trucks`, `POST jobs`, `POST places`, `POST materials`, `POST foremen` | JSON with the display name and any other field → 201 `{ driver }` / `{ truck }` / `{ job }` / `{ place }` / `{ material }` / `{ foreman }`, or 400 `{ fields }` (missing name, a name already in the list ignoring case, unknown usual Truck or Job, a kind not in the list, a usual Foreman who is unknown or removed, or on a Place that is not a job site) |
| `PATCH <list>/:id` (drivers, trucks, jobs, places, materials, foremen) | JSON with only the fields to change, including `active: true/false` → 200 with the entry as for POST; 400 as for POST; 404 if it does not exist. There is no delete: an entry is made inactive. A new entry has no `sortOrder`, and bringing one back (`active` false to true) clears it, so both go last |
| `PUT drivers/order`, `PUT places/order`, `PUT materials/order` | JSON `{ order: [id, …] }`, the whole list first to last (removed entries may be included) → 200 `{ drivers }` / `{ places }` / `{ materials }`, every entry including removed ones, in the new order. Each id gets `sortOrder` 1, 2, 3…; entries left out get none. 400 `{ fields: { order } }` if it is not a list of ids of that list, each once; nothing changes then |
| `GET drivers/:id/later-days` | `{ laterDays }`: how many days after today (US Eastern) hold one of the Driver's Assignments, for the warning before he is removed. 404 if the Driver does not exist |
| `GET drivers/:id/days/:date` | The Driver view: one Driver's day. A Draft → `{ date, state: 'draft' }` and nothing else, since Drivers see nothing before the Send. A Sent day → `{ date, state: 'sent', sentAt, assignments }`: his Assignments (as `GET assignments` gives them, cancelled ones included) in Dave's order, each with `was`: for a Changed one (`sinceSent` `'changed'`), each of `truckNumber`, `fromPlaceName`, `toPlaceName`, `materialName` and `note` that is not as it was when the day was Sent, with the name it had then (null for empty; a null `truckNumber`, his own Truck); otherwise `{}`. A rename of an entry is not a change. Days before today are read too. 400 `{ fields: { date } }` for a date that is not real; 404 if the Driver does not exist; 405 for anything but a read |
| `GET today` | `{ today, tomorrow, nextWorkingDay }`, dates in US Eastern time; `nextWorkingDay` is the first weekday after today that is not a Holiday (New Year's Day, Memorial Day, Independence Day, Labor Day, Thanksgiving, Christmas; a weekend Holiday is not moved) |
| `GET assignments?date=2026-11-20` | `{ assignments: [{ id, date, driverId, driverName, truckId, truckNumber, fromPlaceId, fromPlaceName, toPlaceId, toPlaceName, materialId, materialName, foremanId, foremanName, note, position, createdAt, updatedAt, changedAt, cancelledAt, sinceSent }], sentAt }` (`cancelledAt` is when ✕ cancelled it on its Sent day, null when it is not cancelled; a cancelled one keeps its place; `sentAt` is when the day was first Sent, null while it is a Draft; `sinceSent` is `'added'` for an Assignment created after the Send, `'changed'` for one whose `changedAt` is after it, otherwise null, also in the answers that add or change one; Place names are short names; `changedAt` is when it last really changed, null until then; a null `truckId` means "His own": the Driver takes his usual Truck) by lane (in the Drivers' order as their list reads, no Driver last), then `position` (its place in the lane, from 0), then creation time. 400 `{ fields: { date } }` without a real date |
| `POST assignments` | JSON `{ date, driverId?, truckId?, fromPlaceId?, toPlaceId?, materialId?, foremanId?, note? }` → 201 `{ assignment }`, last in its lane (its date and Driver, or Unassigned), or 400 `{ fields: { name: message } }` (bad date, unknown Driver, Truck, Place, Material or Foreman, note over 1000 characters). From and To may be the same Place. Unknown fields are ignored. Instead of an id, a Place or Material may be typed by name as `fromPlaceName`, `toPlaceName` or `materialName`: the entry with that name, ignoring case, is linked; a removed (inactive) one is made active again; otherwise a new one is added (a Place with no kind). This happens in the same request: if the Assignment is refused or not saved, nothing is added or brought back. 400 `{ fields }` on that name field for a blank name, one over 100 characters, or a name given together with the field's id |
| `PATCH assignments/:id` | JSON with only the fields to change, of `driverId`, `truckId`, `fromPlaceId`, `toPlaceId`, `materialId`, `foremanId`, `note`, and typed names as for POST: a field left out stays as it is, an empty one (null or `""`) is cleared → 200 `{ assignment }`. A real change of Driver puts it last in his lane (its date and Driver, or Unassigned); a real change sets `updatedAt` and `changedAt` to now and, once the day is Sent, keeps the Assignment's fields as they were before (ids and names, note, position) in the add-only `assignment_changes` record; fields sent as they already are (the same Driver again, say) change nothing, not even those times. On a Sent day a real change of Driver does not move it: the Assignment is cancelled (`cancelledAt` and `changedAt` now, its earlier fields kept) and a copy with the fields sent (the rest as they were, note included) is added last in the new lane, created now, so it is Added → 200 `{ assignment: <the copy>, cancelled: <the first one> }`. A cancelled Assignment cannot be changed: 409 `{ error: 'cancelled', message }` until it is put back. The day is fixed: `date` may be sent only as it is; any other is 409 `{ error: 'day_fixed', message }`. 400 `{ fields }` as for POST; 404 if it does not exist. There is no PUT (405) |
| `POST assignments/copy` | JSON `{ to }` (a date after today) → 201 `{ assignments }`: one new Assignment on `to` for each on today (US Eastern, by the Worker's clock) that is not cancelled, every field kept except the note, which is empty, and the cancelled and changed times. Adds to what `to` already has; copying twice copies twice. Nothing on today → 201 `{ assignments: [] }`. 400 `{ fields: { to } }` for a bad date, a day before today, or today itself |
| `POST assignments/:id/move` | JSON `{ direction }`, `"earlier"` (Do this first) or `"later"` (Do this later) → 200 `{ assignments }`: its lane (its date and Driver, or Unassigned) in its new order, swapped with its neighbour and numbered 0, 1, 2… again. Only the one moved gets `updatedAt` and `changedAt` (and, on a Sent day, its earlier fields kept and the Changed mark); the neighbour that shifted does not. 409 `{ error: 'lane_end', message }` when it is already first (earlier) or last (later); 409 `past_day` on a day before today; 409 `cancelled` for a cancelled one; 400 `{ fields: { direction } }` for any other direction; 404 if it does not exist; 405 for other methods |
| `DELETE assignments/:id` | ✕. On a Draft day → 204, a real delete, nothing kept. On a Sent day it cancels instead → 200 `{ assignment }` with `cancelledAt`, `changedAt` and `updatedAt` now, its earlier fields kept in `assignment_changes`; it stays in its place and the day. One already cancelled is answered as it is. 409 `past_day` on a day before today; 404 if it does not exist |
| `POST assignments/:id/put-back` | Put back: clears `cancelledAt` → 200 `{ assignment }`, with `changedAt` and `updatedAt` now and its earlier fields kept (so it is Changed). One not cancelled is answered as it is, nothing changed. 409 `past_day` on a day before today; 404 if it does not exist; 405 for other methods |
| `POST days/:date/send` | Sends the day to the Drivers → 200 `{ date, sentAt }`. The first Send is recorded; Sending again does nothing and answers the first `sentAt` (no lock, no Send again: ADR 0003). 400 `{ fields: { date } }` for a bad date or a day before today (US Eastern); 409 `{ error: 'nothing_to_send', message }` for a day with no Assignments at all (cancelled ones count as Assignments). No warnings |
| `GET weeks/:monday` | The week strip: `{ days: [{ date, state, unassigned, holiday }] }` for the seven days Monday to Sunday of the week starting on `:monday`. `state` is `none` (nothing planned, never Sent), `draft` (planned, not Sent yet), `sent`, or `changed` (an Assignment Changed or Added since the Send); `unassigned` counts the day's Assignments with no Driver that are not cancelled (a cancelled one is off the day; it still keeps the day from being `none`); `holiday` is the Holiday's name or null. Days before today are read too. 400 `{ fields: { date } }` for a date that is not a real Monday |

Days before today (US Eastern) are read-only. Adding an Assignment on one is 400 `{ fields: { date } }`; copying onto one is 400 `{ fields: { to } }`; changing, moving, deleting, cancelling or putting back an Assignment already on one is 409 `{ error: 'past_day', message }`.

The Worker reads the current time from its environment: `NOW` (an ISO 8601 moment) fixes it, as the tests do; deployed environments leave it unset. The old `orders` table is still in the database, unused.

## Workflow

Short-lived feature branch → pull request into `main` → CI checks + a protected preview linked on the PR → one approval → merge → automatic deploy to shared staging. Details, setup and recovery: [docs/deployment.md](docs/deployment.md).

## Rules for database changes

- Migrations change the schema only; test data goes in `seed/fixture.sql`.
- In a pull request, only add (tables, columns, indexes). Rename or drop in a later release, after nothing uses it. The preview database is shared by open PRs, and on staging the old version runs on the migrated database until the new one is live.
- If CI says two migrations share a number, renumber yours after merging `main`.
