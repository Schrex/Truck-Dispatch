# API

The Worker's HTTP API, which the page uses. Shapes are typed in `shared/types.ts`; the day rules (Working days, Holidays, Changed and Added, day states) are in `shared/days.ts`. Words in capitals are defined in [`GLOSSARY.md`](../GLOSSARY.md).

Under `/api/` standalone or `/truck-dispatch/api/` under the Hub. No sign-in yet; Cloudflare Access protects previews and staging.

Every route that reads a body (including one whose fields are all optional, such as `POST truck-problems/:id/fix`) needs a JSON object: without a JSON `Content-Type` it is 415 `{ error: 'json_required' }`, and a body that is not a JSON object is 400 `{ error: 'invalid_json' }`. This is checked first, before a 404. Where several refusals are listed, they are checked in the order given unless a route says otherwise.

|---|---|
| `GET health` | `{ ok, environment, commit }` |
| `GET drivers`, `GET trucks`, `GET jobs`, `GET places`, `GET materials`, `GET foremen`, `GET customers`, `GET inspection-items` | `{ drivers: [{ id, name, defaultTruckId, sortOrder, active }] }`, `{ trucks: [{ id, number, hcssCode, hcssGuid, active }] }`, `{ jobs: [{ id, name, jobNumber, active }] }`, `{ places: [{ id, shortName, fullName, kind, jobId, usualForemanId, geofenceCode, onTruckMap, sortOrder, active }] }`, `{ materials: [{ id, name, sortOrder, active }] }`, `{ foremen: [{ id, name, active }] }`, `{ customers: [{ id, name, usualPlaceId, active }] }`, `{ "inspection-items": [{ id, label, optional, sortOrder, active }] }`. Drivers, Places, Materials and Inspection items come in Dave's own order (`sortOrder`, 1 first), then those with none (`sortOrder` null) by display name; the other lists by display name (name, number or label): active entries only; `?include=inactive` for every entry. A Place's `kind` is `plant`, `job_site`, `shop`, `yard` or null (Settings offers shop and yard as one, Shop or yard, saved as `shop`); its `geofenceCode` (how a Trip finds it in a Fleet export) is optional text, saved trimmed, empty saved as null; `onTruckMap` is true when it has one, and is never saved (sent, it is ignored). A Truck's `hcssCode` (how an Import finds it: its EquipmentCode in Fleet) is optional text, saved trimmed, empty saved as null. An Inspection item's `optional` is true when a Driver may leave it unanswered. Only a job site has a `usualForemanId`; it is emptied when the Place stops being one, and an Assignment keeps its own Foreman, so changing it never rewrites a planned or past day. A Customer's `usualPlaceId` is optional (null for none) |

Bring it back in Places, or pick another."), a Foreman's or Customer's name that any entry of the other list has, in use or removed, ignoring case, on `name`: "<name> is a Foreman already." / "<name> is a Customer already." When a removed (inactive) entry already has that name, ignoring case, nothing is added: that entry is brought back with the name as written now and the fields sent, the rest as they were, last in an ordered list → 200 with the entry and `broughtBack: true`. A refused request brings nothing back |
| `PATCH <list>/:id` (drivers, trucks, jobs, places, materials, foremen, customers, inspection-items) | JSON with only the fields to change, including `active: true/false` → 200 with the entry as for POST; 400 as for POST; 404 if it does not exist. There is no delete: an entry is made inactive. A new entry of Drivers, Places, Materials or Inspection items (also one typed for an Assignment), and one brought back (`active` false to true), goes last: it gets the `sortOrder` after the highest, after giving every entry still without one a `sortOrder` in the order the list is read, so nothing else moves |
| `PUT drivers/order`, `PUT places/order`, `PUT materials/order`, `PUT inspection-items/order` | JSON `{ order: [id, …] }`, the whole list first to last (removed entries may be included) → 200 `{ drivers }` / `{ places }` / `{ materials }` / `{ "inspection-items" }`, every entry including removed ones, in the new order. | `GET drivers/:id/later-days` | `{ laterDays }`: how many days after today (US Eastern) hold one of the Driver's Assignments, for the warning before he is removed. 404 if the Driver does not exist |
| `GET drivers/:id/next-assigned` | `{ date }`: the first day after tomorrow (US Eastern) that holds one of the Driver's Assigned Assignments that is not cancelled (his Drafts do not count), or null, for the Driver view's "Next from Dave". 404 if the Driver does not exist; 405 for anything but a read. (It was `next-sent`, now 404.) |
| `GET drivers/:id/days/:date` | The Driver view: one Driver's day → `{ date, assignments, truckLog? }`: only his Assigned Assignments (`assignedAt` set; his Drafts are left out, as Drivers see nothing of a Draft), as `GET assignments` gives them, cancelled ones included, in Dave's order. A day with none Assigned answers `assignments: []` ("Nothing from Dave yet"). Each has `was`: for a Changed one (`sinceSent` `'changed'`), each of `truckNumber`, `fromPlaceName`, `toPlaceName`, `atPlaceName`, `materialName`, `forName`, `note`, `work` and `machine` that is not as it was when it was Assigned, with the name it had then (null for empty; a null `truckNumber`, his own Truck); otherwise `{}`. A rename of an entry is not a change. `forName` is For as one field across Foremen and Customers: the Foreman's or Customer's name it had then, given once when it became another entry of either list (Foreman Ed to Customer Jaus is `forName: 'Ed'`); values kept before there were Customers have none, and count as no Customer; likewise values kept before there was At count as no At, and values kept before there were kinds as a Haul with no machine (so nothing changed before shows a false `was`). On today (the Worker's clock, US Eastern) only, it also has `truckLog` (`DriverTruckLog`, `shared/types.ts`): `GET trucks/:truckId/days/:date` with no `at` (as of the latest Import) for the Truck he checked in to that day (his latest Inspection), else his usual Truck, plus that Truck's `hcssCode` for the Truck log's header. It is left out on any other day, when he has no Truck, and while that Truck has no stored visits entered that day. Days before today are read too. 400 `{ fields: { date } }` for a date that is not real; 404 if the Driver does not exist; 405 for anything but a read |
| `GET today` | `{ today, tomorrow, nextWorkingDay }`, dates in US Eastern time; `nextWorkingDay` is the first weekday after today that is not a Holiday (New Year's Day, Memorial Day, Independence Day, Labor Day, Thanksgiving, Christmas; a weekend Holiday is not moved) |
| `GET assignments?date=2026-11-20` | `{ assignments: [{ id, date, driverId, driverName, truckId, truckNumber, fromPlaceId, fromPlaceName, toPlaceId, toPlaceName, atPlaceId, atPlaceName, materialId, materialName, foremanId, foremanName, customerId, customerName, note, work, machine, position, createdAt, updatedAt, changedAt, cancelledAt, assignedAt, handedFromId, sinceSent }] }`, Drafts and Assigned ones alike. For is `foremanId`/`foremanName` or `customerId`/`customerName`, never both (both null when blank). At (`atPlaceId`, `atPlaceName`) is the Place the Truck works at, beside From and To; null when none. `work` is the kind of work, `haul` (the default, and every Assignment made before there were kinds), `move` (an equipment move) or `other`; `machine` is a Move's machine as typed, null on any other kind. `assignedAt` is when Dave Assigned it, null for a Draft; `handedFromId` is, on the copy made by giving an Assigned Assignment to another Driver, the id of the one it was handed over from, otherwise null; `cancelledAt` is when ✕ cancelled it (only an Assigned one is cancelled), null when it is not cancelled, and a cancelled one keeps its place; `sinceSent` is `'added'` for one Assigned on its own day (US Eastern) or handed over (`handedFromId` set), `'changed'` for one whose `changedAt` is after its `assignedAt`, otherwise null (always null on a Draft), also in the answers that add, change or Assign one; Place names are short names; `changedAt` is when it last really changed, null until then; a null `truckId` means "His own": the Driver takes his usual Truck. An optional `trips` (the Trip part: `{ loads, tons, status, since, lastLoadAt, truckingHours }`, phase 3, `shared/types.ts`; `loads` is null for an At-only Haul, whose At Trips count toward `status`, `since` and `truckingHours` but never Loads) is sent on each Assignment a stored Trip matched that day: for every Truck with stored visits entered on that US Eastern date, the Worker builds the Truck's whole day as `GET trucks/:truckId/days/:date` opens it with no `at` (as of the latest Import that covered it) and attaches each Assignment's Trip part from that answer. Drafts, Assignments no stored Trip matched and every Assignment on a day with no stored visits have no `trips`, so such a day answers exactly as before. The board block shows it; `GET drivers/:id/days/:date` sends the same Trip parts on the Driver's own cards. On such a day the answer also has `trucks`: one `{ truckId, truckNumber, unplanned, whichAssignment }` (`DayTruck`) per Truck with stored visits, from the same whole-Truck day (its `lanes`, below). `unplanned` is each piece of Unplanned work as `{ id, places, leftAt, arrivedAt, driver }` (`places` short names else geofence codes, in order; `driver` `{ id, name }` of the latest check-in to the Truck that day at or before `leftAt`, null with none: the board's "Driver not known · Truck 55" row); `whichAssignment` is each Trip two or more Assignments fit equally as `{ id (its leftAt), from, to, assignmentIds }`, never Unplanned work. With no stored visits that day `trucks` is left out. Listed by lane (in the Drivers' order as their list reads, no Driver last), then `position` (its place in the lane, from 0), then creation time. 400 `{ fields: { date } }` without a real date |
| `POST assignments` | JSON `{ date, work?, driverId?, alsoDriverIds?, truckId?, fromPlaceId?, toPlaceId?, atPlaceId?, materialId?, foremanId?, customerId?, machine?, note? }` → 201 `{ assignment, assignments }`, a Draft, last in its lane (its date and Driver, or Unassigned), or 400 `{ fields: { name: message } }` (bad date, unknown Driver, Truck, Place, Material, Foreman or Customer, note over 1000 characters, `work` not `haul`, `move` or `other` ("Pick Haul, Move or Other."), `machine` not text or over 100 characters). `work` left out is `haul`. Each kind uses only its own fields: a Haul For, At, Material, From and To; a Move `machine`, From and To; Other none of them (Driver, Truck and note are every kind's; an Other's text is its note), e.g. `{ fields: { fromPlaceId: 'Other has no From.' } }`. A field the kind does not use sent with a value (by id or typed name) is refused on that field, e.g. `{ fields: { materialId: 'A Move has no Material.' } }` or `{ machine: 'A Haul has no machine.' }`; sent empty it is no harm. For is at most one of `foremanId` and `customerId`: a body setting both is 400 `{ fields: { customerId: 'Pick a Foreman or a Customer, not both.' } }` (the page shows it on For). `alsoDriverIds` (a list of Driver ids) makes the same Assignment for each of those Drivers too, one each, last in his own lane: `assignments` holds them all, `driverId`'s first, which is also `assignment`. They are saved in one batch, all or none. 400 `{ fields: { alsoDriverIds } }` if it is not a list of ids, names a Driver twice (or `driverId` again), is sent without `driverId`, or names a Driver who is removed or does not exist. From, To and At may be the same Place. Unknown fields are ignored. Instead of an id, a Place or Material may be typed by name as `fromPlaceName`, `toPlaceName`, `atPlaceName` or `materialName`: the entry with that name, ignoring case, is linked; a removed (inactive) one is made active again; otherwise a new one is added (a Place with no kind). For may be typed as `forName`: an active Foreman with that name, else an active Customer, else a removed Foreman, else a removed Customer (brought back), else a new Customer; a typed For never adds a Foreman. It sets one of `foremanId` and `customerId` and clears the other. This happens in the same request: if the Assignment is refused or not saved, nothing is added or brought back. 400 `{ fields }` on that name field for a blank name, one over 100 characters, or a name given together with the field's id |
| `PATCH assignments/:id` | JSON with only the fields to change, of `driverId`, `truckId`, `fromPlaceId`, `toPlaceId`, `atPlaceId`, `materialId`, `foremanId`, `customerId`, `note`, `work`, `machine`, and typed names as for POST: a field left out stays as it is, an empty one (null or `""`) is cleared → 200 `{ assignment }`. Setting For (a `foremanId` or `customerId`, or `forName`) clears the other of the two in the same save; clearing one leaves the other; both set is refused as for POST. A change of `work` clears, in the same save, every field the new kind does not use (a Move: Material, For and At; a Haul: the machine; Other: Material, For, At, From, To and the machine), keeping the Driver, Truck and note (and From and To between Haul and Move); once it is Assigned that is a change like any other (Changed, with `was.work` the kind it was). A change that keeps `work` (left out or sent as it is) and sets a field the kind does not use is refused on that field as for POST, never dropped. A real change of Driver puts it last in his lane (its date and Driver, or Unassigned); a real change sets `updatedAt` and `changedAt` to now and, once it is Assigned, keeps its fields as they were before (ids and names, note, position) in the add-only `assignment_changes` record; fields sent as they already are (the same Driver again, say) change nothing, not even those times. A Draft's change of Driver simply moves it. Once it is Assigned, a real change of Driver does not move it: it is cancelled (`cancelledAt` and `changedAt` now, its earlier fields kept) and a copy with the fields sent (the rest as they were, note included) is added last in the new lane, created now: given to a Driver, the copy is Assigned at once (`assignedAt` now, `handedFromId` the first one's id, so it is Added); given to Unassigned, it is a Draft → 200 `{ assignment: <the copy>, cancelled: <the first one> }`. | `POST assignments/:id/move` | JSON `{ direction }`, `"earlier"` (Do this first) or `"later"` (Do this later) → 200 `{ assignments }`: its lane (its date and Driver, or Unassigned) in its new order, swapped with its nearest neighbour that is not cancelled (cancelled ones keep their place and are stepped over) and numbered 0, 1, 2… again. Days before today (US Eastern) are read-only. Adding an Assignment on one is 400 `{ fields: { date } }`; Start from onto one is 400 `{ fields: { date } }` and Copy to onto one 400 `{ fields: { to } }`; changing, moving, Assigning, deleting, cancelling or putting back an Assignment already on one is 409 `{ error: 'past_day', message }`.

The Inspection checklist starts with the paper form's 12 items (ids `insp-01` to `insp-12`, `sortOrder` 1–12), loaded by `seed/inspection-items.sql` in every environment; re-running it only adds missing items, so a rename, reorder or removal stays.

Inspections are append-only: the Worker never changes or deletes one (or its answers), and the database refuses an update to `inspections` or `inspection_answers` (a trigger). The database does not block a delete, since the tests clear the tables between tests; nothing in the Worker deletes them. `doneAt` is an ISO 8601 moment in UTC, shown in US Eastern; whether an Inspection needs repair is worked out from its answers. Truck problems are kept forever (`truck_problems`); only `fixed_at` and `fixed_note` are ever set, once. Their reporting Driver is nullable in the schema, so Dave adding problems later needs no table rebuild, but the Worker requires one for now.

The Worker reads the current time from its environment: `NOW` (an ISO 8601 moment) fixes it, as the tests do; deployed environments leave it unset. The old `orders` table is still in the database, unused.
